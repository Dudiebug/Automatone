# M5.1 — Controller item and binding

## Metadata

- State: PLANNED
- Milestone: M5
- Depends on: M4.5, per the approved chunk-loading and automatic-resume addition
  is stated by the plan.
- Risk: high
- Sensor profiles: default, architecture_sensitive, runtime_minecraft
- Approved plan reference: plan lines 563-597.

## Objective

Register one Automatone Controller item with versioned server-owned binding data
so one controller identifies one owned worker during normal play and inventory
synchronization.

## Why this task exists

The controller is the single user-facing handle for one worker. Binding must be
server-authoritative and simple enough that later menu and packet handlers can
derive identity from trusted context.

## Allowed scope

- Controller item registration.
- Versioned worker UUID data component.
- Server interaction binding to an owned worker.
- Server ownership validation and explicit simple rebinding.

## Explicitly forbidden / out of scope

- Multiple workers per controller or worker fleets.
- Client-trusted identity or client-side binding writes.
- GUI tabs, dashboards, storage, catch-up work while the server is stopped/paused, or unrelated packet flow.
- A second scanner, pathfinder, target queue, movement engine, or mining
  algorithm.

The mandatory shared architecture, exclusion, quantity, GUI-gate, and
Milestone 5 gate rules are in INDEX.md under Global architecture contract,
Explicitly out of scope through Milestone 6, Quantity semantics, GUI gate and
first implementation slice, and Milestone 5 gate.

## Implementation constraints

- Store only one versioned binding identity; dimension is optional diagnostic
  data, not a second worker mapping.
- Binding writes and ownership validation are server authoritative.
- Keep rebinding explicit and simple.
- Do not start M5 UI/network product flow until the scheduled gates pass.
