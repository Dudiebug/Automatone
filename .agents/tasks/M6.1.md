# M6.1 — Persist ownership, binding, and product state

## Metadata

- State: PLANNED
- Milestone: M6
- Depends on: INFERRED M5.5 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: critical
- Sensor profiles: default, architecture_sensitive, runtime_minecraft,
  persistence, network_security
- Approved plan reference: plan lines 712-744.

## Objective

Persist only the planned identity, ownership, binding, configuration,
source-block progress, session state, and last failure code, with one shared
ownership policy.

## Why this task exists

The MVP must survive save/restart without turning transient native runtime
state into a serialized job/path engine. Ownership also must mean the same
thing for binding, menu open, Start, and Stop.

## Allowed scope

- Worker identity and owner UUID.
- Controller worker binding.
- Target block ID.
- Finite quantity/unlimited.
- Successful source-block progress.
- Session state.
- Last useful failure code.
- Shared ownership checks for binding, menu open, Start, and Stop.

## Explicitly forbidden / out of scope

- A* paths, path nodes, ore positions, scan generations, partial break
  progress, or active Automatone process internals.
- Catch-up mining, automatic retry, job queues, or persistent
  pathfinding.
- A second scanner, pathfinder, target queue, movement engine, or mining
  algorithm.
- Client/GUI authority for persistence or authorization.

The mandatory shared rules are in INDEX.md#global-architecture-contract,
INDEX.md#quantity-semantics, INDEX.md#explicitly-out-of-scope-through-milestone-6,
and INDEX.md#milestone-6-gate.

## Implementation constraints

- Persist only understandable product state listed by the plan.
- Never persist paths, scan generations, partial break progress, or active
  native process internals.
- Keep ownership server authoritative and centralized.
- Reconstruct transient runtime from current world state in M6.2.

## Approved chunk-loading integration (2026-09-06)

The authoritative addition is docs/M4_JOBS_AND_CHUNK_LOADING.md. M4.5 provides
chunk tickets, inventory/job persistence and automatic resume. M5 bindings include
UUID plus dimension and preserve server-side ownership checks at any distance.
M6 hardens this behavior; older no-loading/manual-restart assumptions are superseded.

## Approved M5 UI integration

docs/M5_GUI_CONTROLLER.md supersedes single-worker item binding and single-target
assumptions. M6 starts after M5.8 acceptance and hardens owner rosters, personal
profiles/overrides, archived inventories, multi-target paused jobs and per-run
notifications. M5 already persists these features. Holders have their own roster;
new workers start empty. Preserve M5 migration and automatic RUNNING-only resume.
