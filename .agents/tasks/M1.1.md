# M1.1 — Lock the source baseline

## Metadata

- State: PLANNED
- Milestone: M1
- Depends on: none explicitly; no task-level dependency is stated by the plan.
- Risk: medium
- Sensor profiles: default, architecture_sensitive
- Approved plan reference: plan lines 28-56 and 176-183.

## Objective

Produce an auditable comparison and import decision for the server-worker-relevant
upstream behavior that will be ported.

## Why this task exists

The plan uses the fork's 1.20 branch as the closest existing version baseline,
while the newer upstream repository is only a behavioral reference. A bounded
ledger prevents unrelated client and MineFortress behavior from entering the
NeoForge server mining path.

This task establishes what may be reimplemented later and why. It does not
start product implementation and does not grant acceptance to any current
implementation note.

## Allowed scope

- Compare this fork's 1.20 branch against minefortress-mod/automatone:main for
  server-worker-relevant changes.
- Record the upstream reference commit SHA.
- Bring forward only the behavior needed for Baritone, MineProcess, entity
  context, input/controller handling, world scanning, and required accessors.
- Avoid wholesale merging unrelated client or MineFortress features.

## Explicitly forbidden / out of scope

- Wholesale upstream merges or cherry-picks.
- MineFortress-specific APIs or ownership hooks.
- Fake-player networking, client fake-player types, player-behavior mixins,
  advancement/sleep/chunk-tracking exceptions, or testmod fake-player work.
- Global mob MoveControl, LookControl, or JumpControl mixins.
- Unrelated command, renderer, notification, metadata, test-deletion, or
  publication changes.
- Worker, product mining, GUI, menu, or network implementation.
- GUI work before Milestone 3 passes.

The full global architecture contract and excluded-feature list are preserved
in INDEX.md.

## Preflight questions

1. What current symbols/classes already own each proposed behavior?
2. What callers and dependencies are affected by each proposed port?
3. Does similar functionality already exist in the fork?
4. Which architecture boundaries could an upstream import cross?
5. What deterministic source comparison or review artifact directly observes
   success?
6. Which upstream changes are truly required for the native server mining path,
   and which are merely adjacent behavior?
7. Is any proposed exception to the locked ledger supported by compile or
   runtime evidence, or is it only an assumption?

## Implementation constraints

- The ledger is the complete M1.1 import decision.
- Later upstream code requires an approved ledger amendment containing commit,
  behavior, and reason before implementation.
- Use the exact three immutable baseline references above.
- Preserve the consumer-thin and native-Automatone ownership boundaries in
  INDEX.md.
- All task states remain PLANNED until bootstrap and independent verification
  establish a clean accepted baseline.
