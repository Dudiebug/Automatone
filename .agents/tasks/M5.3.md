# M5.3 — Start/Stop payloads and centralized server validation

## Metadata

- State: PLANNED
- Milestone: M5

  is stated by the plan.
- Risk: critical

  network_security
- Approved plan reference: plan lines 620-638.

## Objective

Implement minimal intent-based Start/Stop payloads with centralized server-side
context, identity, ownership, block, quantity, and busy-state validation before
any product or native state mutation.

## Why this task exists

The client proposes intent; the server owns identity, authorization, world
mutation, and product state. Centralized validation prevents forged packets from
reaching the worker or native process and gives later status updates a trusted
state source.

## Allowed scope

- Minimal intent-based Start/Stop payloads.
- Trusted controller/menu-derived worker identity.
- All listed Start validation checks.
- Matching Stop context/ownership checks.
- Validated delegation to product session and native MineProcess.

## Explicitly forbidden / out of scope

- Client-trusted worker identity, coordinates, ownership, progress, or
  authorization.
- State mutation before complete validation.
- A second scanner, pathfinder, target queue, movement engine, mining
  algorithm, or task queue.
- Automatic retries, offline work, storage, or GUI authority.

## Implementation constraints

- Validate all listed conditions before any product/native mutation.
- Derive identity from server-owned context.
- Keep payloads intent-based and minimal.
- Use the one product Stop method and native MineProcess path.
- Authorization and world mutation remain server authoritative.
