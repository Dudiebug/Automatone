# M5.4 — Authoritative status/progress updates

## Metadata

- State: PLANNED
- Milestone: M5
- Depends on: INFERRED M5.3 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: high
- Sensor profiles: default, architecture_sensitive, runtime_minecraft,
  network_security
- Approved plan reference: plan lines 640-654.

## Objective

Send meaningful server-owned state snapshots so the GUI displays current target,
amount mode, progress, state, and error without inferring authority from
animation or inventory.

## Why this task exists

Users need feedback while the server remains the only authority. Explicit
snapshots at meaningful transitions prevent stale screens and avoid turning
client animation or inventory observation into a second product state machine.

## Allowed scope

- Meaningful server snapshot events listed in the plan.
- Snapshot fields for target, amount mode, progress, state, and last error.
- Client display of server state.
- Ordering coverage for immediate completion/failure.

## Explicitly forbidden / out of scope

- Client-inferred or client-mutated authority.
- Client target coordinates or worker authority.
- Dashboards, telemetry history, logs, maps, or storage controls.
- Duplicate mining, pathing, or scanning engine.

The mandatory shared rules are in INDEX.md#global-architecture-contract,
INDEX.md#quantity-semantics, INDEX.md#explicitly-out-of-scope-through-milestone-6,
and INDEX.md#milestone-5-gate.

2. Which payload/handler path sends snapshots and to whom?

4. Which completion/failure ordering race can expose stale state?

## Implementation constraints

- Snapshots originate from server-owned state.
- Send on the exact meaningful events in the plan.
- Do not infer progress from inventory, drops, or animation.
- Keep status/error codes and display text separable as later failure mapping
  requires.
