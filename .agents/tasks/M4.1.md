# M4.1 — Add the minimal mining session and progress callback

## Metadata

- State: PLANNED
- Milestone: M4
- Depends on: INFERRED M3.4 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: high
- Sensor profiles: default, architecture_sensitive, runtime_minecraft
- Approved plan reference: plan lines 477-505.

## Objective

Add the smallest server-owned MiningSession state and successful-target-break
callback so only requested source blocks increment progress.

## Why this task exists

Native MineProcess quantity is inventory/item based. The product needs a
separate, small server-owned source-block counter without reimplementing native
discovery, pathing, movement, or mining.

## Allowed scope

- Target block registry ID.
- Finite requested source-block amount or unlimited.
- Matching source blocks successfully broken.
- States IDLE, RUNNING, COMPLETED, CANCELLED, FAILED.
- Last error placeholder.
- Successful-destruction callback with source-block-only counting.

## Explicitly forbidden / out of scope

- Counting attempts, drops, pickups, inventory items, or unrelated obstructions.
- A second scanner, pathfinder, target queue, movement engine, or mining
  algorithm.
- GUI, networking, persistence, storage, or worker-fleet behavior.
- Bypassing native MineProcess behavior.

The mandatory global architecture, quantity, exclusion, GUI-gate, and
milestone-gate rules are in INDEX.md under Global architecture contract,
Quantity semantics, Explicitly out of scope through Milestone 6, GUI gate and
first implementation slice, and Milestone 4 gate.

## Preflight questions

1. What current native break-completion callback can distinguish target and
   obstruction blocks?
2. Which callers own product session state and can create duplicate sessions?
3. Does any existing state already count source blocks?
4. Which server/main-thread boundary protects progress mutation?
5. What GameTest directly observes target, obstruction, drop, pickup, and
   pre-existing-inventory behavior?
6. Which future product-state and fixture paths are UNKNOWN?

## Implementation constraints

- Progress is server authoritative and changes only after actual matching
  destruction.
- Keep the state object minimal.
- Native MineProcess remains the discovery/pathing/mining engine.
- Do not persist or count transient path/break internals here.
