# M1.4 — Minimize mixins and restore native MineProcess

## Metadata

- State: PLANNED
- Milestone: M1
- Depends on: INFERRED M1.3 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: critical
- Sensor profiles: default, architecture_sensitive, runtime_minecraft
- Approved plan reference: plan lines 216-238.

## Objective

Retain only server-core mixins/accessors required by pathing/mining and make the
real Baritone MineProcess, scanner/cache chain, asynchronous publication, and
cancellation usable without client runtime dependencies.

## Why this task exists

Native mining is the product's pathing and process engine. The port must expose
the real MineProcess and preserve its scanner, cache, filters, async
publication, and cancellation behavior without relying on obsolete Yarn hooks
or client notification paths.

The plan specifically calls for public 1.21.1 APIs where possible and leaves
world-backed dedicated-server proof to M1.5.

## Allowed scope

- Audit each existing mixin/accessor and retain only those truly required by the
  server pathing/mining core.
- Prefer public 1.21.1 APIs or consumer-worker-local behavior over broad
  mob/player mixins.
- Update required mixin targets and descriptors.
- Restore the real Baritone#getMineProcess(), scanner/cache dependency chain,
  block filters, async calculation publication, and cancellation behavior.
- Remove client notification/render dependencies from the server mining path.

## Explicitly forbidden / out of scope

- Broad mob, player, or fake-player hooks retained for convenience.
- Client notification, toast, renderer, HUD, or fake-player paths.
- Worker break behavior, quantity semantics, GUI, networking, or persistence.
- Treating current MineProcessLifecycleTest or the plan's historical
  Implemented note as accepted proof.
- A consumer scanner, pathfinder, target queue, or mining engine.
- GUI work before Milestone 3 passes.

The full global architecture contract, quantity semantics, and excluded-feature
list are preserved in INDEX.md.

## Preflight questions

1. Which current mixins/accessors are actually called by server pathing/mining?
2. Which callers and dependencies cross the scanner/cache/process boundary?
3. Does a public 1.21.1 API replace each private or injected hook?
4. Which client-only, fake-player, or broad mob boundary is at risk?
5. What deterministic test observes native process activation, cancellation,
   stale async publication, and scanner offsets?
6. Can negative-height movement and scanner section offsets be checked
   independently as the plan requires?

## Implementation constraints

- Keep the retained mixin list small and documented.
- Use public 1.21.1 APIs where possible.
- The real native MineProcess remains owned by Automatone.
- Cancellation must invalidate stale outstanding scans and async publications.
- Do not move process failure logic into a consumer adapter.
- Required runtime evidence is UNVERIFIED when unavailable.
