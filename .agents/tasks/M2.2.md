# M2.2 — Attach one explicit Automatone runtime

- Approved plan reference: plan lines 284-325.

## Objective

Attach exactly one explicitly owned Automatone runtime to each loaded worker,
tick it once per server tick, and dispose or recreate it with the worker
lifecycle.

## Why this task exists

The worker must not rely on automatic component attachment. Explicit ownership
makes duplicate runtime creation, duplicate ticks, unload cleanup, and reload
reconstruction observable and bounded.

The runtime is transient. Persistence of product state and restart semantics
are Milestone 6 concerns, not a reason to serialize path or process internals.

## Allowed scope

- Construct exactly one runtime per loaded worker.
- Supply the worker entity context and controller explicitly.
- Tick the runtime exactly once per server tick.
- Cancel or unregister on unload or removal.
- Recreate one fresh transient runtime after reload.

## Explicitly forbidden / out of scope

- Automatic CCA/component lookup or duplicate runtime ownership.
- Persisting active runtime, path, or process internals.
- Worker fleets, multiple runtimes per worker, job queues, or offline operation.
- Movement, mining, GUI, networking, or quantity logic beyond lifecycle wiring.
- GUI work before Milestone 3 passes.

The full global architecture contract, quantity semantics, and excluded-feature
list are preserved in INDEX.md.

## Implementation constraints

- Runtime ownership is explicit and singular.
- Tick the runtime once per server tick; avoid recursive or duplicate lookups.
- Runtime state is transient and must not become a persistence engine.
- Removal/disposal is deterministic and idempotent.
- No chunk tickets, offline work, auto-resume, or product queue.
