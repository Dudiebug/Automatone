# M3.1 — Implement worker break-state and targeting semantics

## Metadata

- State: PLANNED
- Milestone: M3
- Depends on: INFERRED M2.4 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: high
- Sensor profiles: default, architecture_sensitive, runtime_minecraft
- Approved plan reference: plan lines 373-408.

## Objective

Implement one focused server-side worker break-state machine whose reach, eye
position, rotation, and raycast target agree with native Automatone intent and
reset safely.

## Why this task exists

Native Automatone supplies the path and break intent, but the non-player worker
needs a small controller that can represent progressive interaction states and
validate a survival-like target reach. Keeping this adapter focused avoids
rebuilding player or mining behavior in the consumer.

Milestone 3 is the first mining proof and is a hard gate before GUI work.

## Allowed scope

- Idle, start, continue, and complete states.
- Target change.
- Abort/reset.
- Out-of-reach or invalid target.
- Worker removal.
- Actual eye position/rotation and defined survival-like reach.
- Agreement between native selected-block/raycast view and controller target.

## Explicitly forbidden / out of scope

- A second scanner, A*, pathfinder, target-position queue, movement engine, or
  mining algorithm.
- GUI, menu, networking, quantity, persistence, or storage behavior.
- Consumer-provided target coordinates as a replacement for native discovery.
- GUI work before Milestone 3 passes.
- Broad adapter logic hiding native failures.

The full global architecture contract, quantity semantics, and excluded-feature
list are preserved in INDEX.md.

## Implementation constraints

- Keep one small state machine in the worker controller.
- Use actual server-side eye/rotation/raycast data.
- Reset state on target change, invalid/reach failure, cancel, and removal.
- Native Automatone remains responsible for discovery and movement.
- No GUI before this milestone's full gate passes.

## Milestone completion gate

M3 cannot be complete until all of these plan gates pass:

- One direct native mine(block) call finds the target without consumer
  coordinates.
- The worker walks to and faces or reaches it.
- Normal positive-hardness progressive breaking succeeds.
- Normal destruction and drop behavior occurs.
- Mid-break cancel works.
- The consumer has no second mining, search, or pathing engine.
- The mining GameTest passes consistently.

M3.1 supplies targeting/state evidence only; later M3 tasks supply destruction
and native one-block proof.
