# M1.3 — Remove Fabric/Quilt/CCA runtime ownership

## Metadata

- State: PLANNED
- Milestone: M1
- Depends on: INFERRED M1.2 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: high
- Sensor profiles: default, architecture_sensitive, runtime_minecraft
- Approved plan reference: plan lines 199-214.

## Objective

Give Automatone an explicit Java-owned runtime and world-provider lifecycle with
one server tick/disposal path and no Fabric, Quilt, or Cardinal Components
runtime ownership.

## Why this task exists

The approved architecture replaces component-managed lifetime with explicit
ownership. A non-player worker needs a predictable runtime and per-level
provider without a CCA lookup or a hidden lifecycle that can duplicate ticks or
retain removed hosts.

This task removes ownership coupling only. Worker adaptation and native mining
proof remain later tasks.

## Allowed scope

- Remove Cardinal Components inheritance and key lookups from IBaritone,
  controllers, entity context, and world context.
- Replace component factories with ordinary constructors or factories.
- Define the smallest explicit runtime and per-level world-provider lookup
  required by Automatone internals.
- Define one server tick/disposal lifecycle and ensure removed hosts cannot
  retain live runtimes.

## Explicitly forbidden / out of scope

- A generic NeoForge replacement for CCA.
- Fake-player bridges, broad global mob mixins, worker product behavior, GUI,
  or networking.
- Reintroducing Fabric or Quilt runtime ownership under another name.
- Dedicated-server construction proof; that is explicitly M1.5.
- Treating the plan's historical Implemented note as acceptance evidence.
- GUI work before Milestone 3 passes.

The full global architecture contract, quantity semantics, and excluded-feature
list are preserved in INDEX.md.

## Preflight questions

1. What current runtime/provider symbols and callers already own lifecycle?
2. Which API, main, launch, and test dependencies cross the provider boundary?
3. Does an explicit provider or ordinary factory already exist in the candidate?
4. Which lifecycle edges can duplicate ticks or retain removed hosts?
5. What focused lifecycle test and server runtime fixture directly observe
   creation, tick, removal, and disposal?
6. Are any future worker-host context paths present? If not, record UNKNOWN.

## Implementation constraints

- Construct or inject the world provider directly as required by the locked
  ledger; do not retain a CCA key lookup.
- Keep lifecycle ownership explicit and singular.
- Disposal must be idempotent.
- Do not add generic component semantics or move worker/product ownership into
  Automatone.
- Required runtime evidence is UNVERIFIED when unavailable.
