# M5.5 — Networking tests and manual GUI acceptance

## Metadata

- State: PLANNED
- Milestone: M5
- Depends on: INFERRED M5.4 scheduling edge; no explicit task-level dependency
  is stated by the plan.
- Risk: critical
- Sensor profiles: default, architecture_sensitive, runtime_minecraft,
  network_security
- Approved plan reference: plan lines 656-708.

## Objective

Reject the complete invalid-packet matrix and document one dedicated-server/client
manual flow proving binding, searchable selection, authoritative progress,
completion, unlimited Start, and Stop.

## Why this task exists

This is the Milestone 5 security and user-flow closure. Automated tests prove
forged or invalid requests cannot mutate server state; the manual flow proves
the compact MVP is usable end to end without making the client authoritative.

## Allowed scope

- Every automated negative case listed in the plan.
- The exact ten-step manual flow listed in the plan.
- Packet tampering, server-authority, and one-screen/native scope review.

## Explicitly forbidden / out of scope

- Omitting/softening a negative test.
- Treating manual success as authorization proof.
- Extra GUI surfaces, fleets, queues, storage, telemetry, or duplicate engines.
- Execution before Milestone 3 and prior scheduled task gates are accepted.

## Preflight questions

1. Which payload handlers and server state can each negative case mutate?
2. Which binding/menu/session symbols are used by the manual flow?
3. Does each listed rejection have an existing test or fixture?

   while server authority is bypassed?
5. What artifact records the exact manual ten-step sequence and state?
6. Are the test fixtures and manual environment paths present? Otherwise record
   UNKNOWN.

## Implementation constraints

- Preserve every listed negative case and manual step.
- Assert pre/post server state on rejection.
- Observe server-owned 0-to-1-to-2 progress and Stop cessation.
- Keep client authority absent.
- A missing required network/runtime measurement is UNVERIFIED.
