## Contract and implementation boundary

Five global pages: Overview, Batch jobs, Collection, Retired and Settings.
Overview preserves selection and offers Start/Pause/Resume/Stop/Retire with
eligibility and per-worker outcomes. Busy replacement and retirement use one
server-owned confirmation. Keep individual cards/details and compact scrolling.
Batch jobs combine selected existing workers and 0..10 new workers with a shared
target list, per-worker quantity/unlimited, destination, and deploy-only/start.
Fill to 10 selects all active workers and computes free slots including pending
reservations. Validate every reference/owner/revision before mutation. Unavailable
owned workers report individual failures; foreign/stale references reject.

New-worker kits use one explicitly selected real tool per worker and up to eight
material variants/counts per worker, defaulting to 64 cobblestone. Preview exact
components, aggregate available/required counts and shortages. Menu owns copied
inventory snapshot/revision and preview tokens; client slot references cannot
supply item contents. Any shortage blocks the whole submission. Changed inventory
before confirmation rejects without reservations or worker mutation. At each
successful deployment commit revalidate and consume only that worker's actual
kit; later shortages fail that worker without consuming supplies. If any failure
occurs after a worker has received supplies, retire it with all contents.

Reserve all new slots before starting existing workers or preparation. Extend the
existing four-concurrent WorkerRelocation service with a bounded queue and commit
hook; do not add a terrain/movement engine. Menu closure preserves progress;
logout/shutdown cancel queued/preparing children, release tickets/reservations,
and leave unused supplies with the player. Successful children remain. Persist
bounded per-worker request outcomes for the current server lifetime/reopened UI.
