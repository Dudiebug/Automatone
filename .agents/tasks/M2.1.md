## Objective

Register a minimal non-player server-side worker whose inventory, held item, and
selected slot can satisfy Automatone's host contract, with deterministic
spawn/despawn coverage.

## Why this task exists

Milestone 2 attaches native Automatone to one server-side worker. The first
bounded change is a worker shell that supplies only the inventory and selected
slot behavior the native tool-selection path needs.

The consumer owns worker adaptation, but does not own pathfinding, scanning, or
mining. The approved worker subproject and fixture paths are listed below; these are
planned additions, not existing implementation.

## Allowed scope

- Register one worker entity with only required attributes.
- Expose inventory, held item, and selected-slot semantics needed by Automatone
  tool switching.
- Add a GameTest helper or test spawn path instead of building placement UX yet.

## Explicitly forbidden / out of scope

- Wandering, combat, following, storage behavior, or product AI.
- Runtime attachment or movement engine beyond the host shell.
- Fake client/player input infrastructure.
- A custom scanner, pathfinder, target-position queue, movement engine, or
  mining algorithm.
- Placement UX, GUI, networking, quantity, or persistence.
- GUI work before Milestone 3 passes.

The full global architecture contract, quantity semantics, and excluded-feature
list are preserved in INDEX.md.

## Implementation constraints

- Keep the worker minimal and server-side.
- Use the worker's vanilla Container and selected-slot access as the host
  contract where the actual API supports it.
- Do not add product AI or client placement UX.
- Preserve native Automatone ownership of tool-selection decisions.
- A missing fixture or runtime sensor is UNVERIFIED.
